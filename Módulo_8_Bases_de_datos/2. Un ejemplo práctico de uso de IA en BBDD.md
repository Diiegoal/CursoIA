## Un ejemplo práctico de uso de IA en bases de datos

En 2026, la forma de usar IA con bases de datos ha cambiado radicalmente. Ya no se trata de copiar schemas al chat y pegar queries de vuelta: el patrón dominante es conectar Claude Code (o Cursor) directamente a la BBDD vía un MCP server, de forma que el agente introspecciona el esquema, ejecuta EXPLAIN ANALYZE, lee pg_stat_statements y propone cambios sobre datos reales.

En esta sección cubrimos los casos de uso más comunes del día a día de un developer con BBDD, usando Claude Code + DBHub (MCP) como herramienta principal y un Postgres local en Docker como banco de pruebas. Al final verás un ejemplo completo end-to-end sobre un sistema de reserva de bicicletas.

**Qué vamos a cubrir:**

- Setup: Claude Code + DBHub + Postgres en Docker
- Diseño y revisión de esquemas con IA (Prisma / Drizzle)
- Queries SQL simples y complejas con introspección real
- Índices, normalización y revisión de migraciones destructivas
- Unificación de múltiples bases de datos
- pgvector: convertir Postgres en vector store para RAG
- Análisis de rendimiento: MCP vs PGAdmin
- Ejemplo completo: sistema de reserva de bicicletas con Claude Code + MCP

> ⚠ **Nota importante para 2026:** si vienes de un workflow "ChatGPT + copy-paste", este es el cambio de mayor impacto que vas a incorporar. El agente conectado a la BBDD reduce drásticamente los errores de copia y hace posibles loops de optimización reales (propone índice → lo crea en dev → re-ejecuta EXPLAIN → mide mejora).

## 0. Setup: Claude Code + DBHub + Postgres en Docker

Antes de los ejemplos, dejamos un entorno listo. Esto es lo que todo alumno debe tener funcionando al final de los primeros 15 minutos de sesión.

### Paso 1: Levantar Postgres local con Docker

```bash
docker run --name ai4devs-pg \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_USER=dev \
  -e POSTGRES_DB=bikerental \
  -p 5432:5432 \
  -d postgres:17
```

### Paso 2: Añadir DBHub como MCP server a Claude Code

DBHub (bytebase/dbhub) es un MCP server universal de base de datos zero-dependency que soporta Postgres, MySQL, SQL Server, MariaDB y SQLite. Lo elegimos porque es ligero, está activamente mantenido y tiene modo `--readonly` para producción.

Desde la raíz del proyecto, ejecuta:

```bash
claude mcp add --transport stdio db -- npx -y @bytebase/dbhub \
  --dsn "postgres://dev:devpass@localhost:5432/bikerental?sslmode=disable"
```

Para entornos con datos reales (staging, prod), añade `--readonly`:

```bash
claude mcp add --transport stdio db-prod -- npx -y @bytebase/dbhub \
  --readonly \
  --dsn "postgres://readonly:pass@prod.example.com:5432/app"
```

En modo read-only, DBHub solo permite SELECT, SHOW, DESCRIBE y similares; bloquea INSERT, UPDATE, DELETE y DDL. Es tu red de seguridad contra el "oops" del agente.

Arranca Claude Code y prueba:

Si el agente responde sin que tengas que pegar nada, ya tienes el loop cerrado. 🎉

## 1. Creación y revisión de estructuras de bases de datos

Veamos cómo la IA puede ayudar en el diseño, revisión y optimización de estructuras de BBDD, y cómo implementar estos cambios usando Prisma o Drizzle (ver nota al final de la sección sobre cuál elegir).

### Diseño de esquemas de bases de datos

El diseño de esquemas implica definir entidades, atributos y relaciones que representan los datos y las reglas de negocio. Un buen diseño debe ser:

- **Normalizado:** seguir las formas normales para reducir redundancia y mejorar integridad.
- **Escalable:** capaz de manejar el crecimiento de datos y queries sin degradar rendimiento.
- **Mantenible:** fácil de entender, modificar y extender a medida que evolucionan los requisitos.

La IA puede ayudar en el diseño analizando los requisitos de negocio y proponiendo una estructura optimizada. Dado el siguiente fragmento de requisitos:

> "El servicio de renta de bicicletas permite a los usuarios alquilar bicis por horas o días. Cada bicicleta tiene un número de identificación único, un modelo y un estado (disponible, alquilada, en mantenimiento). Los usuarios proporcionan nombre, correo y teléfono al registrarse."

Le pedimos a Claude Code: "Genera el schema Prisma correspondiente y escríbelo en `prisma/schema.prisma`." Resultado esperado:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  rentals     Rental[]
}

model Bicycle {
  id      Int      @id @default(autoincrement())
  model   String
  status  String
  rentals Rental[]
}

model Rental {
  id        Int      @id @default(autoincrement())
  user      User     @relation(fields: [userId], references: [id])
  userId    Int
  bicycle   Bicycle  @relation(fields: [bicycleId], references: [id])
  bicycleId Int
  startTime DateTime
  endTime   DateTime
}
```

### Revisión y optimización de estructuras existentes

A medida que los requisitos evolucionan, es importante revisar periódicamente la estructura. Con MCP, la IA puede hacerlo sobre la BBDD real, no sobre un screenshot. El agente puede:

- Detectar entidades o columnas redundantes e identificar la redundancia con datos reales (`SELECT COUNT(DISTINCT address) FROM "User"` te dice si vale la pena normalizar).
- Recomendar normalización hasta 3NF.
- Sugerir índices en columnas usadas frecuentemente (introspeccionando pg_stat_statements).
- Identificar relaciones faltantes o FKs sin definir.

Por ejemplo, si añadimos el requisito de almacenar la dirección, Claude Code propone una nueva entidad Address con relación 1:1:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  address     Address?
  rentals     Rental[]
}

model Address {
  id       Int    @id @default(autoincrement())
  street   String
  city     String
  state    String
  zipCode  String
  user     User   @relation(fields: [userId], references: [id])
  userId   Int    @unique
}
```

### Ejemplo: diseño completo desde requisitos detallados

Requisitos extendidos:

- Los usuarios pueden alquilar bicis por horas o días.
- Cada bicicleta tiene ID único, modelo, estado y ubicación actual (lat/long).
- Los usuarios proporcionan nombre, email, teléfono y dirección.
- Pueden tener una tarjeta de crédito para pagos recurrentes.
- Se registra historial de alquileres y reseñas/calificaciones.

Claude Code produce este schema optimizado:

### Nota sobre Prisma vs Drizzle en 2026

Los dos ORMs TypeScript líderes hoy son Prisma y Drizzle. Ambos son válidos y el máster usa Prisma por defecto, pero conviene que sepas cuándo elegir cada uno:

| Criterio | Prisma | Drizzle |
|---|---|---|
| Filosofía | Schema-first, abstrae el SQL | Code-first en TS, cerca del SQL |
| DX / onboarding | Excelente, gentle learning curve | Requiere más confort con SQL |
| Edge / Serverless | Prisma 7 (finales 2025) eliminó el engine en Rust, bundle mucho menor | Rey del edge: bundle ~7KB, zero dependencies |
| Migraciones | `prisma migrate` muy integrado | `drizzle-kit` más manual, más control |
| Studio / UI | Prisma Studio | Drizzle Studio |
| Quién debería usarlo | Equipos que vienen de ORMs clásicos, SaaS en Node/Next.js | Edge workers, Cloudflare Workers, equipos SQL-first |

Regla simple: si el proyecto se despliega en Vercel/Node clásico → Prisma. Si va a Cloudflare Workers o necesitas mínimo cold start → Drizzle.

## 2. Consultas SQL: simples y complejas

Con el MCP conectado, el flujo cambia: en lugar de pedirle a la IA que escriba una query, le pides que resuelva un problema de negocio y ella misma introspecciona el schema, compone la query, la ejecuta y te devuelve resultados.

### Queries básicos

"Dame todos los usuarios registrados."

```sql
SELECT * FROM "User";
```

"Dame todas las bicicletas que están alquiladas ahora mismo."

```sql
SELECT * FROM "Bicycle" WHERE status = 'alquilada';
```

"Dame el nombre del usuario y el modelo de la bici para los alquileres activos." Con JOINs:

```sql
SELECT "User".name, "Bicycle".model
FROM "Rental"
INNER JOIN "User" ON "Rental"."userId" = "User".id
INNER JOIN "Bicycle" ON "Rental"."bicycleId" = "Bicycle".id
WHERE "Rental"."endTime" IS NULL OR "Rental"."endTime" > NOW();
```

### Queries avanzados

"Quiero, por bici, el número total de alquileres y la duración media en horas."

```sql
SELECT
  "Bicycle".id,
  "Bicycle".model,
  COUNT("Rental".id) AS total_rentals,
  AVG(EXTRACT(EPOCH FROM "Rental"."endTime" - "Rental"."startTime") / 3600) AS avg_rental_hours
FROM "Bicycle"
LEFT JOIN "Rental" ON "Bicycle".id = "Rental"."bicycleId"
GROUP BY "Bicycle".id, "Bicycle".model;
```

Nota el LEFT JOIN: incluye bicis que nunca se alquilaron. La IA debería explicártelo al generarla.

### Optimización de queries

"Las 10 bicis más alquiladas junto con su ubicación actual."

```sql
SELECT
  "Bicycle".id,
  "Bicycle".model,
  "Location".latitude,
  "Location".longitude,
  COUNT("Rental".id) AS total_rentals
FROM "Bicycle"
INNER JOIN "Location" ON "Bicycle"."locationId" = "Location".id
INNER JOIN "Rental" ON "Bicycle".id = "Rental"."bicycleId"
GROUP BY "Bicycle".id, "Bicycle".model, "Location".latitude, "Location".longitude
ORDER BY total_rentals DESC
LIMIT 10;
```

Con MCP, el siguiente paso es automático: Claude Code ejecuta EXPLAIN ANALYZE sobre esta query y te dice si hay sequential scans problemáticos. Si los hay, propone índices y los crea en dev para medir la mejora.

### Ejemplo avanzado: CTEs y window functions

Supón que necesitas, para el panel de control:

- Top 5 usuarios con más alquileres del último mes, con total de alquileres y horas totales.
- Para cada uno de esos usuarios, la bici que alquiló más veces y su ubicación actual.

> ⚠ **Atención al patrón "top-N por grupo":** en PostgreSQL NO existe `LIMIT 1 PER USER`. Es un error común que la IA puede soltar si no la corriges. El patrón correcto es `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` o `DISTINCT ON`.

Query correcta usando ROW_NUMBER():

```sql
WITH top_users AS (
  SELECT
    "User".id,
    "User".name,
    COUNT("Rental".id) AS total_rentals,
    SUM(EXTRACT(EPOCH FROM "Rental"."endTime" - "Rental"."startTime") / 3600) AS total_rental_hours
  FROM "User"
  INNER JOIN "Rental" ON "User".id = "Rental"."userId"
  WHERE "Rental"."startTime" >= DATE_TRUNC('month', CURRENT_DATE - INTERVAL '1 month')
    AND "Rental"."endTime" IS NOT NULL
  GROUP BY "User".id, "User".name
  ORDER BY total_rentals DESC
  LIMIT 5
),
ranked_bicycles AS (
  SELECT
    top_users.id AS user_id,
    "Bicycle".id AS bicycle_id,
    "Bicycle".model,
    "Location".latitude,
    "Location".longitude,
    COUNT("Rental".id) AS times_rented,
    ROW_NUMBER() OVER (
      PARTITION BY top_users.id
      ORDER BY COUNT("Rental".id) DESC
    ) AS rn
  FROM top_users
  INNER JOIN "Rental" ON top_users.id = "Rental"."userId"
  INNER JOIN "Bicycle" ON "Rental"."bicycleId" = "Bicycle".id
  INNER JOIN "Location" ON "Bicycle"."locationId" = "Location".id
  GROUP BY top_users.id, "Bicycle".id, "Bicycle".model, "Location".latitude, "Location".longitude
)
SELECT
  tu.name,
  tu.total_rentals,
  tu.total_rental_hours,
  rb.model AS most_rented_bicycle,
  rb.latitude,
  rb.longitude
FROM top_users tu
JOIN ranked_bicycles rb ON rb.user_id = tu.id AND rb.rn = 1;
```

**Técnicas aplicadas:**

- CTEs (`WITH ... AS`) para dividir la query en pasos reutilizables.
- Agregaciones (COUNT, SUM, EXTRACT) para métricas temporales.
- Window function `ROW_NUMBER() OVER (PARTITION BY ... )` para obtener el top-1 por grupo — este es el patrón correcto, no existe `LIMIT 1 PER USER` en Postgres.
- Filtrado por fecha con DATE_TRUNC e INTERVAL.
- JOINs para combinar usuarios, alquileres, bicis y ubicaciones.

## 3. Índices, normalización y revisión de migraciones

### Índices

Los índices son estructuras de datos que aceleran la recuperación. Funcionan como punteros directos a filas con un valor específico en una o más columnas. Conectado vía MCP, Claude Code puede leer pg_stat_statements y proponer índices basados en las queries reales que más CPU consumen en tu BBDD, no en suposiciones.

Para el servicio de bicis:

```sql
CREATE INDEX idx_rental_starttime ON "Rental" ("startTime");
CREATE INDEX idx_rental_endtime   ON "Rental" ("endTime");
CREATE INDEX idx_bicycle_status   ON "Bicycle" (status);
```

Índices compuestos cuando varias columnas aparecen juntas en WHERE:

```sql
CREATE INDEX idx_rental_user_bicycle ON "Rental" ("userId", "bicycleId");
```

### Normalización hasta 3NF

Ejemplo: inicialmente guardamos la dirección como columnas sueltas en User:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  street      String
  city        String
  state       String
  zipCode     String
  rentals     Rental[]
  reviews     Review[]
}
```

La IA detecta que street, city, state, zipCode dependen funcionalmente del ID de usuario y propone extraer una tabla Address:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  address     Address?
  rentals     Rental[]
  reviews     Review[]
}

model Address {
  id      Int    @id @default(autoincrement())
  street  String
  city    String
  state   String
  zipCode String
  user    User   @relation(fields: [userId], references: [id])
  userId  Int    @unique
}
```

### 🔴 Revisión humana OBLIGATORIA de migraciones destructivas

Este es el punto más crítico de la sesión. Generar migraciones con IA es fácil; el riesgo real está en aplicarlas sin revisar. Antes de ejecutar cualquier migración, pide explícitamente a Claude Code:

> "Revisa la migración generada y dime: ¿hay DROP COLUMN, DROP TABLE, CREATE UNIQUE sobre datos existentes, o ALTER TYPE que pueda truncar? Para cada caso, dime el riesgo y cómo hacerlo sin pérdida de datos."

Patrón seguro para eliminar una columna en producción:

1. Dejar de escribir en la columna en el código (feature flag).
2. Desplegar.
3. Esperar N días para validar que nada falla.
4. Ejecutar `ALTER TABLE ... DROP COLUMN` en una ventana de mantenimiento.

Nunca: `prisma migrate deploy` en producción sin haber leído el SQL generado en `prisma/migrations/*`.

> 🚨 **Prueba esto ahora**
>
> Introduce deliberadamente un cambio destructivo en tu `schema.prisma` (p. ej. renombrar phoneNumber a phone). Ejecuta `npx prisma migrate dev --create-only`. Pídele a Claude Code que lea el SQL generado y te avise de los riesgos. Verifica que detecta el ALTER TABLE DROP COLUMN implícito.

## 4. Unificación de múltiples bases de datos

Cuando una aplicación tiene varias BBDDs, es común encontrar redundancias e inconsistencias. Con MCP, el agente puede conectarse a las múltiples fuentes simultáneamente (configuras varios MCP servers con ID diferente, p. ej. db-users, db-bikes, db-reviews) y ejecutar queries cruzadas para detectar problemas.

Supón:

BBDD de usuarios:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  address     String
}
```

BBDD de bicis y alquileres:

```prisma
model Bicycle {
  id      Int      @id @default(autoincrement())
  model   String
  status  String
  rentals Rental[]
}

model Rental {
  id        Int      @id @default(autoincrement())
  userId    Int
  bicycleId Int
  startTime DateTime
  endTime   DateTime
}
```

**Problemas que Claude Code detecta al conectarse a ambas:**

- `User.address` como string plano → difícil de actualizar, inconsistencias por typos.
- No hay FK real entre `Rental.userId` y `User.id` (viven en BBDDs distintas) → nada impide huérfanos.
- No hay garantías de integridad referencial cross-db.

**Estrategia de unificación:**

1. Crear un schema unificado con las entidades combinadas.
2. Establecer FKs explícitas.
3. Normalizar (extraer Address).
4. Migrar datos con scripts que transformen lo necesario.

Schema unificado propuesto:

```prisma
model User {
  id          Int      @id @default(autoincrement())
  name        String
  email       String   @unique
  phoneNumber String
  address     Address?
  rentals     Rental[]
}

model Address {
  id      Int    @id @default(autoincrement())
  street  String
  city    String
  state   String
  zipCode String
  user    User   @relation(fields: [userId], references: [id])
  userId  Int    @unique
}

model Bicycle {
  id      Int      @id @default(autoincrement())
  model   String
  status  String
  rentals Rental[]
}

model Rental {
  id        Int      @id @default(autoincrement())
  user      User     @relation(fields: [userId], references: [id])
  userId    Int
  bicycle   Bicycle  @relation(fields: [bicycleId], references: [id])
  bicycleId Int
  startTime DateTime
  endTime   DateTime?
}
```

### Caso con tercera BBDD (reseñas desnormalizadas)

Si hay una BBDD extra con:

```prisma
model Review {
  id           Int    @id @default(autoincrement())
  userEmail    String
  bicycleModel String
  rating       Int
  comment      String
}
```

Observa que Review referencia por userEmail y bicycleModel en vez de IDs — patrón típico de BBDDs que crecieron sin coordinación. Para migrar al schema unificado, Claude Code puede generar:

```sql
-- 1. Crear tabla Review en BBDD unificada
CREATE TABLE "Review" (
  id         SERIAL PRIMARY KEY,
  rating     INT NOT NULL,
  comment    TEXT,
  "userId"   INT NOT NULL REFERENCES "User"(id),
  "bicycleId" INT NOT NULL REFERENCES "Bicycle"(id)
);

-- 2. Resolver userEmail → userId y bicycleModel → bicycleId
INSERT INTO "Review" (rating, comment, "userId", "bicycleId")
SELECT
  r.rating,
  r.comment,
  u.id AS "userId",
  b.id AS "bicycleId"
FROM legacy.reviews r
JOIN "User" u ON u.email = r."userEmail"
JOIN "Bicycle" b ON b.model = r."bicycleModel"
WHERE u.id IS NOT NULL AND b.id IS NOT NULL;

-- 3. Identificar reseñas huérfanas para revisión manual
SELECT * FROM legacy.reviews r
LEFT JOIN "User" u ON u.email = r."userEmail"
LEFT JOIN "Bicycle" b ON b.model = r."bicycleModel"
WHERE u.id IS NULL OR b.id IS NULL;
```

Siempre ejecuta el paso 3 antes del paso 2: las reseñas huérfanas (usuarios borrados, modelos discontinuados) deben revisarse manualmente, no descartarse en silencio.

## 5. pgvector: Postgres como vector store para RAG

Este bloque no existía en el material anterior y es probablemente el caso de uso de IA+BBDD de mayor crecimiento en 2025–2026. Si no puedes cubrir todo el contenido en la sesión, prioriza este bloque.

### ¿Qué es pgvector?

pgvector es una extensión de PostgreSQL que añade un tipo de columna vector para almacenar embeddings de alta dimensión y operadores de búsqueda por similitud. Permite usar Postgres como vector database sin añadir otra pieza (Pinecone, Weaviate, Qdrant) al stack.

**Cuándo usarlo vs. vector DB dedicada:**

| Escenario | Elige |
|---|---|
| Ya tienes Postgres y necesitas semantic search o RAG con menos de 10M vectores | `pgvector` |
| Los vectores conviven con datos relacionales (usuarios, productos, docs) | `pgvector` (JOINs con tu data existente) |
| Necesitas más de 50M vectores y latencia sub-10ms | Vector DB dedicada |
| MVP / prototipo | `pgvector` siempre |

### Setup

Usa la imagen `pgvector/pgvector:pg17` en lugar de `postgres:17`:

```bash
docker run --name ai4devs-pgv \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_USER=dev \
  -e POSTGRES_DB=ragdemo \
  -p 5432:5432 \
  -d pgvector/pgvector:pg17
```

En psql o vía Claude Code:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### Esquema: documentos con embeddings

```sql
CREATE TABLE documents (
  id         SERIAL PRIMARY KEY,
  content    TEXT NOT NULL,
  metadata   JSONB,
  -- 1024 = dimensiones de Voyage AI voyage-3
  -- 1536 = OpenAI text-embedding-3-small
  -- 3072 = OpenAI text-embedding-3-large
  embedding  VECTOR(1024),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

> ⚠ **Cuidado con las dimensiones:** deben coincidir exactamente con las del modelo de embedding que uses. Cambiar de modelo = reindexar todo.

### Generar embeddings

Ejemplo en Node.js usando Voyage AI (la recomendación de Anthropic para embeddings):

```ts
// scripts/embed.ts
import { VoyageAIClient } from "voyageai";
import { PrismaClient } from "@prisma/client";

const voyage = new VoyageAIClient({ apiKey: process.env.VOYAGE_API_KEY });
const prisma = new PrismaClient();

async function embedAndStore(content: string, metadata: object = {}) {
  const response = await voyage.embed({
    input: [content],
    model: "voyage-3",
  });

  const embedding = response.data[0].embedding;

  // Prisma no tiene soporte nativo de vector aún; usamos $executeRaw
  await prisma.$executeRaw`
    INSERT INTO documents (content, metadata, embedding)
    VALUES (
      ${content},
      ${JSON.stringify(metadata)}::jsonb,
      ${`[${embedding.join(",")}]`}::vector
    )
  `;
}
```

### Búsqueda por similitud

```sql
-- <=> es el operador de distancia coseno de pgvector
-- <-> distancia euclídea; <#> producto interno
SELECT
  id,
  content,
  metadata,
  1 - (embedding <=> $1::vector) AS similarity
FROM documents
ORDER BY embedding <=> $1::vector
LIMIT 5;
```

### Índice HNSW para producción

Hasta unas 10k filas puedes vivir con búsqueda exacta. A partir de ahí, crea un índice aproximado:

```sql
CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

- `m`: número de conexiones por nodo (16 es el default razonable).
- `ef_construction`: calidad del índice durante build (mayor = más lento construir pero mejor recall).
- Para queries: ajusta `SET hnsw.ef_search = 100;` en sesión para más recall a cambio de latencia.

### Búsqueda híbrida: semántica + filtros relacionales

La ventaja killer de pgvector frente a una vector DB separada: combinar similarity search con WHERE clauses sobre columnas regulares en la misma query.

```sql
-- "Docs sobre 'devolución de bicicletas' publicados este mes
--  y que pertenezcan al tenant 42"
SELECT
  d.id,
  d.content,
  1 - (d.embedding <=> $1::vector) AS similarity
FROM documents d
WHERE d.metadata->>'tenant_id' = '42'
  AND d.created_at >= DATE_TRUNC('month', NOW())
ORDER BY d.embedding <=> $1::vector
LIMIT 10;
```

Esto en Pinecone requiere malabares con metadata filtering; en Postgres es SQL normal.

## 6. Análisis de rendimiento: MCP vs PGAdmin

PGAdmin sigue siendo útil en 2026, pero con MCP el flujo de trabajo cambia drásticamente. Te damos ambos enfoques y cuándo usar cada uno.

### Con MCP (flujo recomendado 2026)

Desde Claude Code, le pides:

> "Identifica las 10 queries más lentas de la última hora (usa pg_stat_statements), ejecuta EXPLAIN ANALYZE en cada una, y dime cuáles se beneficiarían de índices. Propón los CREATE INDEX y justifica cada uno."

El agente ejecuta algo como:

```sql
SELECT
  substring(query, 1, 100) AS query_preview,
  calls,
  ROUND((total_exec_time / calls)::numeric, 2) AS avg_ms,
  ROUND(total_exec_time::numeric, 2) AS total_ms
FROM pg_stat_statements
WHERE query NOT LIKE 'EXPLAIN%'
  AND calls > 10
ORDER BY total_exec_time DESC
LIMIT 10;
```

Después itera: EXPLAIN ANALYZE sobre las top candidates, propone índice, lo crea en dev, re-ejecuta, compara tiempos. Un loop que en PGAdmin requiere unos 20 clicks.

Requisito: tener pg_stat_statements habilitado. En `postgresql.conf`:

```
shared_preload_libraries = 'pg_stat_statements'
```

Y en la BBDD: `CREATE EXTENSION pg_stat_statements;`

### Con PGAdmin (flujo visual/tradicional)

PGAdmin sigue siendo excelente cuando:

- Quieres explorar visualmente una BBDD nueva que nunca has visto.
- Debugging one-off: ver datos en una tabla, editar una fila manualmente.
- Workshops / formación con audiencia no técnica.
- Revisar dashboards de conexiones, locks, actividad.

Flujo típico para detectar queries lentas:

1. Query Tool en la BBDD de interés.
2. Ejecuta para queries en curso:

```sql
SELECT
  pid,
  NOW() - pg_stat_activity.query_start AS duration,
  query,
  state
FROM pg_stat_activity
WHERE (NOW() - pg_stat_activity.query_start) > INTERVAL '1 minute'
ORDER BY duration DESC;
```

3. Para EXPLAIN de una query sospechosa:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM "Rental"
WHERE "startTime" BETWEEN '2026-01-01' AND '2026-12-31';
```

4. Interpreta el plan. Si ves Seq Scan sobre tabla grande con filtro selectivo → probablemente falte índice.

### Pro tip: dashboard combinado

El flujo óptimo en 2026: PGAdmin abierto para **observar** (dashboard de actividad, locks en tiempo real) + Claude Code conectado por MCP para **actuar** (proponer índices, refactorizar queries, revisar migraciones). Cada uno en lo que es bueno.

## Conclusiones

En estos ejemplos hemos explorado cómo la IA, conectada directamente a la BBDD vía MCP, transforma el trabajo del developer en diseño, implementación y optimización de bases de datos.

El cambio clave de 2024 a 2026 no está en los fundamentos (SQL, normalización, índices siguen siendo lo mismo que enseñaba Codd hace 50 años) sino en el loop de trabajo: antes pegabas schemas en un chat y copiabas queries de vuelta; ahora el agente introspecciona tu BBDD, ejecuta EXPLAIN ANALYZE, mide el impacto real de un índice y propone el siguiente paso basándose en datos, no en suposiciones.

Tres principios que deben quedar claros:

1. **La IA es una herramienta, no un reemplazo.** Sigue siendo tu responsabilidad entender qué hace la migración antes de ejecutarla, especialmente en producción. Nunca aceptes un `prisma migrate deploy` sin haber leído el SQL.
2. **Read-only por defecto en producción.** `--readonly` en DBHub, roles de Postgres sin permisos de escritura, y revisión humana obligatoria de cualquier DDL. El coste de esta fricción es bajo; el coste de no tenerla es perder datos.
3. **pgvector es la puerta de entrada a RAG** y la mayoría de proyectos Node.js modernos con features de IA deberían empezar ahí antes de añadir una vector DB separada. Sólo cruza ese puente cuando el volumen o la latencia lo justifiquen.

A medida que la IA sigue avanzando, el rol del developer con BBDDs se desplaza de "escribir SQL" a "diseñar sistemas, definir constraints de integridad y revisar cambios de alto impacto" — dejando el boilerplate (migraciones simples, queries recurrentes, docs) al agente.
