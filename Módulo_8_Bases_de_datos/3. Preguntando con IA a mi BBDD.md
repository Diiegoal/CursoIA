# 📄 Preguntando con IA a mi BBDD 🔴 — 5 min

**Lia Carrizo**

⏳ Tiempo estimado: 5 min

Tal y como se vio en la introducción a la hora de hablar de análisis de datos, una de las áreas con mayor potencia para la IA es la interacción en lenguaje natural con bases de datos. Simplificar la carga cognitiva que supone crear queries SQL complejas —y la experiencia previa que eso requiere— hace que sea tremendamente útil.

Hoy existen dos grandes vías para conseguirlo, y conviene distinguirlas porque resuelven problemas distintos:

## Vía 1 — Servidores MCP: el flujo nativo del developer (recomendado)

Desde finales de 2024, el Model Context Protocol se ha consolidado como el estándar para conectar cualquier copiloto (Claude Code, Cursor, Windsurf, VS Code/Copilot, Cline) directamente a una base de datos. En la práctica, instalas un servidor MCP para tu motor (Postgres, MySQL, SQLite, Supabase, MongoDB…) y tu IDE pasa a "ver" el esquema, ejecutar queries, explicar planes de ejecución y proponer migraciones sin salir del editor.

👉 **Prueba esto ahora (Postgres / Supabase desde Claude Code):**

```bash
# Postgres genérico
claude mcp add postgres -- npx -y @modelcontextprotocol/server-postgres "$DATABASE_URL?sslmode=require"

# Supabase (OAuth automático, sin PAT manual)
claude mcp add supabase -- npx -y @supabase/mcp-server
```

Luego, desde tu IDE: "Lista las tablas de la BBDD y dime qué índices faltan en `orders` para la query más frecuente del último sprint."

> ⚠ **Seguridad obligatoria:** nunca conectar un MCP en modo escritura contra producción. La práctica estándar es añadir `read_only=true` a la conexión (soportado en Supabase y en el MCP de Postgres) para que la IA no pueda ejecutar INSERT/UPDATE/DELETE/DDL por accidente. Para cambios de esquema, usar una branch de desarrollo o un entorno local.

## Vía 2 — Apps standalone tipo "Chat with your DB": el flujo para equipos no-técnicos

Cuando el consumidor de los datos no es el developer sino negocio, soporte, ventas o dirección, tiene sentido una herramienta empaquetada con UI propia, dashboards y control de acceso granular. Un ejemplo maduro es 🔗[AskYourDatabase](https://www.askyourdatabase.com/), con capa gratuita, conexión a MySQL/Postgres/SQL Server/MongoDB/Snowflake (local o cloud), respuestas en lenguaje natural, devolución de la SQL generada para verificarla (paso imprescindible antes de llevarla a código) y widgets embebibles para producto.

Otras alternativas con tracción real en 2026:

- **Chat2DB** — cliente SQL con text-to-SQL integrado, multi-motor, con cifrado y ejecución local de queries.
- **BlazeSQL** — foco en auto-reportes semanales y visualización; buena integración con Snowflake.
- **WrenAI** (open-source, MIT) — agente text-to-SQL con semantic layer y soporte para OpenAI, Claude, Gemini y Ollama.
- **DataGrip (AI Assistant)** y **TablePlus (BYOK)** — si prefieres un cliente SQL "de siempre" con capacidades de IA encima.

## Regla práctica para decidir

- Eres tú, en tu editor, iterando sobre el código del proyecto → **MCP**.
- Un stakeholder no-técnico necesita consultas ad-hoc recurrentes → **app standalone** (AskYourDatabase / BlazeSQL / WrenAI).
- Vas a ejecutar queries generadas por IA contra datos sensibles → **siempre en read-only**, siempre verificando la SQL antes de aceptarla.
