## 🤖 Reglas para agentes de IA en proyectos backend

Una de las formas más altas de palanca al usar IA en backend es escribir reglas que el agente respete automáticamente cuando genera endpoints, servicios, repos o tests.

**Cursor Rules (formato `.mdc`)**

El antiguo archivo `.cursorrules` quedó deprecado desde Cursor 2.2. La forma actual son archivos `.mdc` dentro de `.cursor/rules/`, con frontmatter YAML:

```mdc
---
description: Patrones backend del proyecto
globs: src/backend/**/*.ts
alwaysApply: false
---
- Toda capa de controller debe delegar en un UseCase, nunca acceder al ORM directamente.
- Los repositorios exponen interfaces, no implementaciones concretas de Prisma.
- Validación de input siempre con Zod antes de entrar al UseCase.
```

**AGENTS.md** — estándar emergente cross-tool (Cursor, Claude Code, Codex, Aider, etc.). Un único archivo en la raíz del proyecto que todos los agentes leen. Soporta anidación: `backend/AGENTS.md`, `frontend/AGENTS.md`, etc.

Recursos:

- docs.cursor.com/context/rules — referencia oficial
- github.com/sanjeed5/awesome-cursor-rules-mdc — colección curada de reglas `.mdc` por stack

> 💡 **Prueba esto ahora:** crea `.cursor/rules/backend-patterns.mdc` con `globs: src/backend/**/*.ts` y escribe 5 reglas que reflejen tu arquitectura (DDD, SOLID, manejo de errores). Pídele al agente que genere un endpoint nuevo y observa cómo cambia respecto a sin reglas.

## 🗄 ORMs y bases de datos — estado 2026

**Prisma** — el ORM por defecto en Node.js/TypeScript.

📣 **Cambio crítico:** Prisma 7 (noviembre 2025) sustituyó el motor Rust por una implementación TypeScript/WASM. Bundle ~85 % más pequeño (14 MB → 1.6 MB), cold starts hasta ~9× más rápidos, y soporte edge nativo. Esto anula casi todas las críticas históricas sobre el peso de Prisma en serverless.

🔗 prisma.io/docs

**Drizzle ORM** — TypeScript-first, SQL-near, footprint ~7.4 kB, sin paso de generación. Sigue siendo la opción fuerte si tu equipo piensa en SQL o deployas a Cloudflare Workers / Vercel Edge.

🔗 orm.drizzle.team

**Zod 4** — validación runtime + inferencia de tipos. La versión 4 (estable en 2025) trae ~14× más velocidad en strings, ~57 % menos bundle, y `@zod/mini` tree-shakable. Se integra de forma natural con Prisma, Drizzle, Hono y tRPC.

🔗 zod.dev

## 🌐 Frameworks HTTP — el mapa en 2026

Express sigue siendo la base instalada (≈76 M descargas/semana), pero en proyectos nuevos el panorama se está moviendo:

| Framework | Cuándo tiene sentido en 2026 |
|---|---|
| **Express** | Rey del ecosistema de middleware, elección segura, máxima compatibilidad con SDKs de terceros. Es el que usamos en el curso. |
| **Fastify** | ~2-3× más rápido que Express para JSON APIs, validación por JSON Schema integrada, `@fastify/express` permite migración incremental. |
| **Hono** | Runtime-agnóstico (Node, Bun, Deno, Cloudflare Workers, Vercel Edge). Ganando cuota rápido en proyectos nuevos y edge. |

## 🧪 Testing de APIs

**Bruno** — cliente HTTP open-source con colecciones guardadas como archivos `.bru` versionables en Git, sin cuenta cloud obligatoria. En 2026 tiene 50 k+ stars y adopción creciente como alternativa a Postman, especialmente en equipos que tratan su API como código.

🔗 usebruno.com

**Bruno CLI** — ejecuta colecciones en CI/CD:

```bash
npm install -g @usebruno/cli
bru run users/ --env Development
```

## 🧠 MCPs útiles para backend

Los MCP (Model Context Protocol) dejan que el agente consulte herramientas externas durante la generación de código — especialmente útil en backend:

- **MCP de Postgres / Prisma** — el agente consulta tu schema y datos reales al generar código, reduciendo alucinaciones de nombres de tablas o columnas.
- **MCP de GitHub** — para que el agente lea issues, PRs o historia de commits como contexto.
- **MCP de Notion / Confluence** — útil si vuestros specs o ADRs viven ahí.

📚 Listado curado oficial: github.com/modelcontextprotocol/servers
