## ¿Por qué estas prácticas importan más (no menos) con IA?

Un copiloto de IA es tan bueno como el contexto que puede cargar y la estructura que puede seguir. Los principios de este capítulo —DDD, SOLID, CUPID, arquitectura hexagonal y patrones— no son "teoría de los 2000": son el vocabulario que le permite a Claude Code, Cursor o cualquier agente de coding razonar sobre tu proyecto sin alucinar. Un backend con fronteras claras (bounded contexts, ports & adapters, servicios con responsabilidad única) produce diffs más pequeños, tests más aislados y agentes más predecibles. Un backend sin esa disciplina convierte a la IA en una fábrica de deuda técnica.

Desarrollar una arquitectura backend robusta y escalable sigue siendo crucial; lo que cambia en 2026 es que la disciplina arquitectónica es también disciplina de contexto.

## 1. Domain-Driven Design (DDD)

El Diseño Guiado por el Dominio es una metodología de desarrollo centrada en modelar el software según la lógica del negocio y el dominio. DDD facilita la creación de sistemas complejos al colocar la comprensión profunda del problema —no el framework— en el centro del diseño.

**Referencia moderna recomendada:** "Learning Domain-Driven Design" de Vlad Khononov (O'Reilly, 2021). Es el puente más accesible al "libro azul" de Eric Evans y el que recomendamos leer primero.

### Ventajas en un flujo con IA

- **Lenguaje ubicuo = mejor prompt.** Cuando tu código, tus specs (S2) y tu conversación con Claude Code usan los mismos términos del negocio, el copiloto deja de inventar nombres.
- **Bounded contexts = unidades de contexto.** Cada contexto acotado cabe en una ventana de contexto manejable. Los agentes trabajan mejor sobre `billing/` que sobre `src/`.
- **Modelos ricos, no anémicos.** La lógica en las entidades (no en "services" gigantes) hace que el código generado por IA sea más revisable y menos propenso a duplicación.

### Componentes clave

- **Entidades:** objetos con identidad propia que atraviesan cambios de estado (un User sigue siendo el mismo usuario aunque cambie su email).
- **Value Objects:** describen aspectos del dominio sin identidad y son inmutables y auto-validados (un Email, un Money, una OrderId). Son el mejor lugar para poner invariantes.
- **Aggregates y Aggregate Root:** un conjunto de objetos tratado como una unidad transaccional. El aggregate root es el único punto de entrada y garantiza que las invariantes del conjunto siempre se cumplan.
- **Repositorios:** interfaces que devuelven y persisten aggregates completos (no tablas).
- **Domain Events:** hechos ocurridos en el dominio (OrderPlaced, PaymentFailed) que desacoplan efectos secundarios y son la base de arquitecturas event-driven.
- **Servicios de dominio:** lógica de negocio que genuinamente no pertenece a una entidad.

### Ejemplo práctico (TypeScript, con aggregate e invariante)

```ts
// Value Object: inmutable, auto-validado
class Money {
  private constructor(
    public readonly amount: number,
    public readonly currency: string
  ) {}

  static of(amount: number, currency: string): Money {
    if (amount < 0) throw new Error('Money amount cannot be negative');
    if (!/^[A-Z]{3}$/.test(currency)) throw new Error('Invalid currency code');
    return new Money(amount, currency);
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('Currency mismatch');
    return Money.of(this.amount + other.amount, this.currency);
  }
}

// Aggregate Root: protege invariantes del conjunto
class Order {
  private constructor(
    public readonly id: string,
    private readonly customerId: string,
    private items: OrderItem[] = [],
    private status: 'draft' | 'placed' | 'paid' = 'draft'
  ) {}

  static create(id: string, customerId: string): Order {
    return new Order(id, customerId);
  }

  addItem(item: OrderItem): void {
    if (this.status !== 'draft') throw new Error('Cannot modify a placed order');
    this.items.push(item);
  }

  place(): OrderPlaced {
    if (this.items.length === 0) throw new Error('Empty order cannot be placed');
    this.status = 'placed';
    return new OrderPlaced(this.id, this.total());
  }

  private total(): Money {
    return this.items.reduce(
      (sum, i) => sum.add(i.subtotal()),
      Money.of(0, 'EUR')
    );
  }
}

// Repository: trabaja con el aggregate completo, no con tablas
interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}
```

## 2. Arquitectura Hexagonal (Ports & Adapters)

Entre DDD (qué) y los patrones concretos (cómo) falta una capa: cómo organizar el código para que el dominio no dependa de frameworks, bases de datos ni librerías. Esa es la arquitectura hexagonal, propuesta por Alistair Cockburn en 2005 y convertida en el estándar de facto para backends Node.js/TypeScript modernos.

### La idea en una frase

Tu lógica de negocio vive en un core que no importa express, ni prisma, ni stripe. Se comunica con el mundo exterior a través de **ports** (interfaces que define el core) implementados por **adapters** (clases que el core nunca ve directamente).

```
┌─ HTTP adapter (Express) ─────────┐
│                                  │
│  ┌────── Core domain ─────┐      │
│  │  Entities              │      │
│  │  Use cases             │──── Port (interface)
│  │  Domain services       │           ▲
│  └────────────────────────┘           │
│                                       │
└─────────── Adapter (PostgreSQL) ──────┘
```

### Por qué es la arquitectura más AI-friendly

- **Tests sin mocks de frameworks.** Pasas un fake del port y listo. Los agentes generan tests triviales.
- **Bounded contexts naturales.** Cada carpeta `src/modules/<dominio>/` es un hexágono independiente que cabe en una ventana de contexto.
- **Separación policy/details.** La IA puede modificar un adapter (detalle) sin tocar el core (policy) y viceversa, sin efectos secundarios cruzados.

### Cuándo NO usarla

- Prototipos, MVPs y CRUDs simples donde la arquitectura añade más ceremonia que valor.
- Equipos sin experiencia previa: la malinterpretación de los ports produce complejidad sin beneficio.

Empieza siempre con arquitectura en capas (controller → service → repository) y refactoriza a hexagonal cuando el dominio pida aislarse del framework. Es la recomendación consensuada en guías de 2025-2026.

## 3. Principios SOLID, DRY y CUPID

### SOLID (Robert C. Martin, 2000)

Cinco principios clásicos de diseño orientado a objetos. Siguen siendo la base de cualquier conversación sobre mantenibilidad, pero en 2026 conviene conocer sus matices.

- **S — Single Responsibility Principle (SRP):** una clase debe tener una única razón para cambiar. Matiz moderno: el propio Uncle Bob aclaró que "razón para cambiar" significa "un único stakeholder/actor del negocio", no "hacer una única cosa".
- **O — Open/Closed Principle (OCP):** abierto a extensión, cerrado a modificación. Se aplica mejor en código tipo librería que en código de aplicación.
- **L — Liskov Substitution Principle (LSP):** los subtipos deben ser sustituibles por sus supertipos sin romper el programa.
- **I — Interface Segregation Principle (ISP):** mejor muchas interfaces pequeñas y específicas que una grande.
- **D — Dependency Inversion Principle (DIP):** los módulos de alto nivel no dependen de los de bajo nivel; ambos dependen de abstracciones. Este es el que habilita la arquitectura hexagonal.

### DRY (Don't Repeat Yourself)

Cada pieza de conocimiento debe tener una representación única y autoritativa en el sistema. Atención a la trampa: duplicación accidental ≠ duplicación conceptual. Dos funciones que hoy son idénticas pero representan reglas de negocio distintas deben permanecer separadas. Unificarlas prematuramente es peor que la duplicación.

### CUPID (Dan North, 2022): la conversación moderna

Dan North —creador de BDD— propuso CUPID como alternativa/complemento a SOLID después de considerar que SOLID había envejecido. No hace falta elegir; en la industria actual se combinan: SOLID para el diseño de clases internas, CUPID para la experiencia global de trabajar con el código.

- **C — Composable:** piezas que combinan bien, con mínimas dependencias.
- **U — Unix philosophy:** hacer una cosa y hacerla bien.
- **P — Predictable:** hace lo esperado, es determinista, observable.
- **I — Idiomatic:** se lee como código "natural" en su lenguaje.
- **D — Domain-based:** la estructura del código refleja el dominio, no los artefactos técnicos (`patient-history/` en lugar de `controllers/`, `models/`, `views/`).

### Ejemplo refactor SRP + DIP (con inyección de dependencias)

```ts
// ❌ Antes: la entidad hace demasiado y depende de infra
class User {
  constructor(public name: string, public email: string) {}
  saveToDatabase(): void { /* conexión a DB */ }
  sendWelcomeEmail(): void { /* SMTP */ }
}

// ✅ Después: SRP + DIP. La entidad no sabe de infra.
class User {
  constructor(
    public readonly id: string,
    public readonly name: string,
    public readonly email: string
  ) {}
}

interface UserRepository {
  save(user: User): Promise<void>;
}

interface EmailService {
  sendWelcome(to: string): Promise<void>;
}

class RegisterUser {
  constructor(
    private readonly users: UserRepository,  // depende de abstracción, no de Postgres
    private readonly email: EmailService     // depende de abstracción, no de SendGrid
  ) {}

  async execute(input: { name: string; email: string }): Promise<User> {
    const user = new User(crypto.randomUUID(), input.name, input.email);
    await this.users.save(user);
    await this.email.sendWelcome(user.email);
    return user;
  }
}
```

## 4. Patrones de diseño (con criterio)

Los patrones son soluciones reutilizables a problemas comunes. Saber identificarlos es más importante que saber implementarlos: muchos lenguajes modernos los ofrecen como primitivas (funciones de primera clase, generators, observables).

### Patrones con vigencia en backend Node.js/TypeScript

- **Factory:** encapsula creación de objetos complejos. Útil cuando la decisión de qué instanciar depende de configuración o input (p.ej. `PaymentProviderFactory` que devuelve un StripeAdapter o un RedsysAdapter).
- **Strategy:** familia de algoritmos intercambiables. En TypeScript moderno suele implementarse con funciones o discriminated unions, no con jerarquías de clases.
- **Observer:** un objeto notifica a otros sobre cambios. En Node.js tienes EventEmitter nativo; en dominios complejos, domain events + event bus.
- **Repository:** (ya visto en DDD) abstrae la persistencia de aggregates.
- **Decorator:** añade comportamiento sin modificar la clase. Base de los interceptores en NestJS y de los middlewares en Express.

### ⚠ Singleton: cuidado

El Singleton se sigue enseñando pero hoy se considera anti-pattern en la mayoría de contextos backend: oculta dependencias, rompe tests (el estado sobrevive entre tests) y dificulta el escalado horizontal. La alternativa moderna es un contenedor de inyección de dependencias (tsyringe, inversify, o DI manual en composition root) que registra una única instancia y la inyecta explícitamente donde se necesita.

Úsalo solo cuando realmente no puedas depender de DI (p.ej. loggers a nivel de proceso), y aun así, hazlo consciente del trade-off.

### Ejemplo: Factory realista

```ts
interface PaymentProvider {
  charge(amountCents: number, token: string): Promise<{ id: string }>;
}

class StripeProvider implements PaymentProvider { /* ... */ }
class RedsysProvider implements PaymentProvider { /* ... */ }

class PaymentProviderFactory {
  static create(providerName: string): PaymentProvider {
    switch (providerName) {
      case 'stripe': return new StripeProvider();
      case 'redsys': return new RedsysProvider();
      default: throw new Error(`Unknown payment provider: ${providerName}`);
    }
  }
}
```

### Patrones modernos que conviene conocer (avanzado)

- **Result / Either type** para manejo de errores tipado sin excepciones (clave en dominios complejos).
- **Unit of Work** para transacciones que abarcan varios repositorios.
- **CQRS** (Command Query Responsibility Segregation) cuando lectura y escritura tienen modelos muy distintos.
- **Saga / Process Manager** para coordinar operaciones distribuidas con compensación.

## Conclusión

Implementar DDD, arquitectura hexagonal, SOLID/CUPID/DRY y patrones de diseño en backend sigue siendo crucial en 2026, y con la llegada de los copilotos y agentes de coding se ha vuelto aún más relevante: un codebase disciplinado no solo es más mantenible para humanos, es también más manejable para la IA que trabaja sobre él.

La regla operativa para este máster: cada vez que escribas código con Claude Code, pregúntate si la estructura que estás creando hace que la próxima iteración del agente sea más fácil o más difícil. Si la respuesta es "más difícil", ese es tu siguiente refactor.
