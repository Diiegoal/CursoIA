En los últimos tiempos, la industria de la tecnología ha promovido con entusiasmo el principio del "shift left" (desplazamiento hacia la izquierda) en el desarrollo de software, impulsando la incorporación de medidas de seguridad desde las etapas iniciales del proceso de desarrollo.&#x20;

# The relative cost of fixing a flaw at different stages of the SDLC

| Stage | Relative Cost |
|---|---|
| REQUIREMENTS / ARCHITECTURE | 1x |
| CODING | 5x |
| INTEGRATION / COMPONENT TESTING | 10x |
| SYSTEM / ACCEPTANCE TESTING | 15x |
| PRODUCTION / POST-RELEASE | 30x |

La meta de esta estrategia es dotar a los programadores de la responsabilidad de asegurar la integridad de su código desde el comienzo del proyecto. Sin embargo, aunque la premisa de este enfoque es loable, la práctica revela una realidad más compleja, en la que confiar exclusivamente en los desarrolladores para la protección de la seguridad en la cadena de desarrollo de software se muestra insuficiente.

En este artículo, propongo una estrategia complementaria de balance: la implementación de barreras de seguridad en el ciclo de vida del desarrollo de software (SDLC) lideradas por el CISO, consistiendo en controles automáticos que ejecutan o aseguran la política de seguridad del SDLC.

## ¿Es el código más o menos seguro si se usan asistentes de IA?

Antes de responder, algunas cifras de un reciente estudio de la startup de ciberseguridad Snyk:

92% said that AI coding tools generate insecure code at least some of the time, but 76% still believe AI-generated code is more secure than human-written code.

The rapid integration of AI tools was found to have not been matched with corresponding advancements in security practices. Fewer than 10% of surveyed teams said that they have implemented automated security checks.

Some 86% of respondents said they are concerned about the security implications of using AI code completion tools. Yet, at the same time, developers believe that because everyone else is using AI coding tools, they must be trustworthy in driving their actions.&#x20;

Nuestra conclusión: como en casi todo, depende. Para nosotros estas herramientas son una oportunidad de incorporar, por defecto y sin esfuerzo, código más seguro. Para otros, solo una manera de hacer código más rápido y con menos esfuerzo.

Saber usar la herramienta, y poner en valor las buenas prácticas en ingeniería de software (en este caso las relativas a ciberseguridad), son 2 ingredientes clave para que la adopción de estas herramientas no se traduzca solo en mayor productividad, sino también en mayor calidad y seguridad.
