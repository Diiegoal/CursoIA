# Agente SRE / DevOps para respuesta a incidentes — Investigación completa

Sí. **Es totalmente posible construir un Agente SRE / DevOps para respuesta a incidentes utilizando prácticamente todo el ecosistema Python**, y además existe evidencia actualizada hasta **septiembre de 2026** de que este patrón ya se está implementando como arquitectura real de agentes. De hecho, OpenAI publicó el **10 de septiembre de 2026** un ejemplo oficial llamado exactamente **“Build an SRE agent for incident response”**. El ejemplo está construido con Python, recibe alertas, investiga telemetría, GitHub, AWS e incidentes anteriores, mantiene una sesión persistente y solicita aprobación humana antes de una acción de rollback.

La respuesta importante a tu pregunta es:

> **Sí puedes hacerlo enteramente con Python.**
>
> **Sí conviene tener backend.**
>
> **LangChain/LangGraph puede ser el cerebro de agente.**
>
> **FastAPI puede ser la capa backend/API.**
>
> **Streamlit es opcional y sirve muy bien como interfaz de administración/prototipo.**
>
> Para una versión verdaderamente empresarial, también entran observabilidad, almacenamiento persistente, workers, seguridad, Kubernetes, Prometheus, Loki, OpenTelemetry, GitHub y algún sistema de incidentes como Alertmanager/PagerDuty/incident.io.

Y hay un detalle muy importante: **en septiembre de 2026 ya no plantearía el proyecto usando la arquitectura vieja de LangChain 0.3.x que se usaba anteriormente**. PyPI muestra **LangChain 1.4.2**, publicada el 18 de septiembre de 2026, y LangGraph aparece en **1.2.11**. LangChain ahora construye sus agentes sobre LangGraph. ([PyPI — LangChain](https://pypi.org/project/langchain/1.4.1/))

# 1. Qué es exactamente este Agente SRE

Un sistema SRE tradicional tiene que responder preguntas como:

> ¿Qué pasó?

> ¿Qué servicio está fallando?

> ¿Desde cuándo?

> ¿Qué cambió antes del fallo?

> ¿Cuántos usuarios están afectados?

> ¿Es aplicación, base de datos, infraestructura, red o despliegue?

> ¿Ha ocurrido antes?

> ¿Qué acción de recuperación corresponde?

Un Agente SRE agrega una capa de razonamiento y orquestación.

La arquitectura conceptual sería:

```text
                   INCIDENTE
                       │
                       ▼
              ┌─────────────────┐
              │ Alert / Webhook │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │ Incident Manager│
              │ deduplicación   │
              │ correlación     │
              └────────┬────────┘
                       │
                       ▼
             ┌────────────────────┐
             │     AI AGENT       │
             │  LangChain/LangGraph│
             └─────────┬──────────┘
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
     Metrics          Logs          Deployments
   Prometheus         Loki            GitHub
        │              │               │
        └──────────────┼───────────────┘
                       ▼
                  AWS / K8s
                       │
                       ▼
                Historial incidentes
                       │
                       ▼
                 Diagnóstico
                       │
                       ▼
              Plan de remediación
                       │
                       ▼
                 ¿Requiere acción?
                    /       \
                  no         sí
                  │           │
                  ▼           ▼
               informar   aprobación
                              │
                              ▼
                       ejecutar acción
                              │
                              ▼
                         verificar
                              │
                              ▼
                         cerrar
                              │
                              ▼
                         postmortem
```

Esto no es una arquitectura inventada para este análisis: es extremadamente cercana al ejemplo oficial de OpenAI publicado en septiembre de 2026. Allí una alerta abre un hilo en Slack, el agente investiga producción, consulta GitHub, AWS e incidentes anteriores y propone rollback, pero la aplicación mantiene la autoridad sobre permisos, deduplicación, historial y aprobación. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

# 3. ¿Dónde entra LangChain?

Aquí existe una distinción importante.

**LangChain no debería ser “el backend completo”.**

LangChain/LangGraph sería la parte de **agent engineering**.

Por ejemplo:

```text
                FastAPI
                   │
                   ▼
             Incident Service
                   │
                   ▼
             LangGraph Agent
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
 Prometheus Tool Loki Tool GitHub Tool
       │           │           │
       ▼           ▼           ▼
    metrics       logs       changes
```

LangChain 1.x proporciona `create_agent`, herramientas, middleware, estado y otras piezas. Sus agentes están construidos sobre LangGraph. ([LangChain docs — Agents](https://docs.langchain.com/oss/python/langchain/agents))

LangGraph está específicamente diseñado para agentes **stateful y long-running**, con infraestructura para:

- ejecución durable
- streaming
- human-in-the-loop
- persistencia
- memoria
- recuperación de ejecución

y sus propios mantenedores lo posicionan para necesidades avanzadas donde se combinan flujos determinísticos y agentic workflows. ([PyPI — LangGraph](https://pypi.org/project/langgraph/))

Esto encaja extraordinariamente bien con SRE.

# 4. ¿Por qué LangGraph es especialmente apropiado aquí?

Un incidente puede tener este estado:

```text
INCIDENT_CREATED

      ↓

TRIAGING

      ↓

COLLECTING_EVIDENCE

      ↓

ANALYZING

      ↓

HYPOTHESIS_CREATED

      ↓

VERIFYING

      ↓

REMEDIATION_PROPOSED

      ↓

WAITING_FOR_APPROVAL

      ↓

REMEDIATION_EXECUTED

      ↓

VERIFYING_RECOVERY

      ↓

RESOLVED

      ↓

POSTMORTEM
```

No quieres que el agente pierda todo si el proceso se reinicia.

LangGraph permite checkpoints y persistencia del estado. La propia documentación indica que `MemorySaver`/`InMemorySaver` no es apropiado para producción porque el estado se pierde al reiniciar y recomienda checkpointers persistentes como `PostgresSaver`. ([LangGraph docs — Persistence](https://docs.langchain.com/oss/python/langgraph/persistence))

Eso es extremadamente importante para incident management.

Imagina:

```text
01:30 AM
│
├── incidente detectado
├── agente investigó 5 herramientas
├── encontró posible regresión
├── propone rollback
│
└── espera aprobación humana
```

Tu servidor se reinicia.

Sin persistencia:

```text
TODO PERDIDO
```

Con persistencia:

```text
incident_id
session_id
thread_id
state
evidence
tool_calls
hypothesis
pending_action
approval_state
```

y puedes continuar.

# 5. Human-in-the-loop es fundamental

Este es uno de los puntos que hacen que el proyecto pase de “chatbot” a sistema profesional.

No deberías permitir:

```text
LLM
 ↓
kubectl delete pod
```

ni:

```text
LLM
 ↓
rollback production
```

directamente.

Una arquitectura mucho más seria es:

```text
Agent
  │
  ▼
"Propongo rollback"
  │
  ▼
Human Approval
  │
 ├── Reject
 │
 └── Approve
        │
        ▼
    Executor
```

LangGraph tiene interrupciones explícitas para detener una ejecución y solicitar entrada humana. En producción recomienda un checkpointer durable y un `thread_id` persistente para poder reanudar la ejecución. ([LangGraph docs — Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts))

También existe middleware específico de LangChain para **Human-in-the-loop approval before high-impact actions**. ([LangChain docs — Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/agents))

# 7. Entonces, ¿necesitas FastAPI?

Para una versión de laboratorio:

**No necesariamente.**

Podrías hacer:

```text
Streamlit
   ↓
LangGraph
   ↓
Prometheus
Loki
GitHub
Kubernetes
```

Pero para una versión profesional:

**Sí recomendaría un backend separado.**

¿Por qué?

Porque necesitas recibir:

- webhooks
- alertas
- eventos de Slack
- eventos de PagerDuty
- eventos de GitHub
- eventos de resolución
- callbacks de aprobación
- solicitudes de usuarios

FastAPI está diseñado para este tipo de capa HTTP y ofrece precisamente características como seguridad, WebSockets, SSE, background tasks, CORS y despliegue. ([FastAPI docs](https://fastapi.tiangolo.com/es/advanced/using-request-directly/))

El ejemplo de OpenAI utiliza precisamente un receptor HTTP con:

```python

async def receive_alert(...):
    ...
```

y la aplicación normaliza el webhook, autentica al emisor y envía la investigación a background. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

# 8. ¿Y Streamlit?

Aquí está la respuesta que estabas buscando:

## Streamlit NO es obligatorio.

Es una **interfaz**, no el agente.

Streamlit tiene una arquitectura cliente-servidor en la que el servidor es Python y el navegador es el cliente. ([Streamlit docs — Architecture](https://docs.streamlit.io/develop/concepts/architecture/architecture))

Puede hacer muy bien:

- chat
- tablas
- gráficos
- métricas
- incident timeline
- botones
- filtros
- estado
- paneles
- resultados del agente

Su API de chat actualmente incluye `st.chat_message`, `st.chat_input`, `st.status` y `st.write_stream`, lo que permite construir interfaces conversacionales y mostrar procesos largos o streaming. ([Streamlit docs — Chat elements](https://docs.streamlit.io/develop/api-reference/chat))

---

# 9. Pero Streamlit tiene una limitación importante

Su `Session State` **no es almacenamiento permanente**.

La documentación de Streamlit indica que:

- la sesión existe mientras la pestaña permanece conectada;
- si se cierra la pestaña, se pierde;
- si el servidor se reinicia, se pierde;
- no es persistencia de negocio. ([Streamlit docs — Session State](https://docs.streamlit.io/develop/concepts/architecture/session-state))

Por lo tanto:

```text
Streamlit Session State
```

no debería contener el estado real del incidente.

El estado real debería estar en:

```text
PostgreSQL
+
LangGraph checkpointer
```

y Streamlit simplemente consultarlo.

# 13. ¿Qué datos necesita el Agente SRE?

Aquí está una parte que suele olvidarse.

Un agente no puede diagnosticar correctamente si solo recibe:

```text
500 Internal Server Error
```

Necesita **evidencia contextual**.

Como mínimo:

## Métricas

```text
request_rate
error_rate
latency
CPU
memory
restarts
queue_depth
database_connections
```

Prometheus dispone de API HTTP para consultas de métricas instantáneas y de rango. ([Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/))

---

## Logs

Loki proporciona API HTTP para:

```text
query
query_range
tail
series
statistics
```

y admite consultas mediante LogQL. ([Grafana Loki HTTP API](https://grafana.com/docs/enterprise-logs/latest/reference/loki-http-api/))

Además, Grafana puede correlacionar logs con métricas y otros datos de observabilidad. ([Grafana — Loki data source](https://grafana.com/docs/grafana/latest/datasources/loki/))

---

## Kubernetes

El agente podría consultar:

```text
pods
deployments
replicasets
services
events
nodes
containers
resource usage
conditions
restart counts
```

La documentación oficial de Kubernetes contempla diagnóstico de Pods, Services, StatefulSets, contenedores y procesos en ejecución. ([Kubernetes — Debugging applications](https://kubernetes.io/docs/tasks/debug/debug-application/))

Y el cliente oficial Python permite trabajar directamente contra la API de Kubernetes. ([GitHub — Kubernetes Python client](https://github.com/kubernetes-client/python))

---

## GitHub

Debe poder consultar:

```text
commits
pull requests
changed files
deployments
statuses
branches
```

GitHub ofrece APIs específicas para pull requests y deployments. ([GitHub REST API — Pulls](https://docs.github.com/en/rest/pulls/pulls))

Esto permite una inferencia crucial:

```text
Error comenzó 13:42
        ↓
Deploy ocurrió 13:37
        ↓
PR modificó Redis pool
        ↓
Error Redis aumentó
```

El agente puede construir esa correlación.

# 15. El flujo de una alerta profesional

Imagina:

```text
checkout-api

error rate:
1.2% → 4% → 12% → 18%
```

Prometheus dispara:

```text
HighErrorRate
```

Alertmanager manda:

```json
{
  "status": "firing",
  "labels": {
    "alertname": "HighErrorRate",
    "service": "checkout-api",
    "severity": "critical"
  }
}
```

FastAPI recibe el webhook.

Entonces el sistema:

```text
1. autentica webhook
2. calcula fingerprint
3. comprueba si incidente ya existe
4. crea/actualiza incidente
5. asigna incident_id
6. crea thread
7. inicia agent session
```

El ejemplo oficial de OpenAI utiliza justamente una relación entre **alert fingerprint → incident → Slack thread → agent session**. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

# 16. Deduplicación es muy importante

Supón que tienes:

```text
alert 1
alert 2
alert 3
alert 4
```

pero todas representan:

```text
checkout-api error spike
```

Sin deduplicación:

```text
4 incidentes
4 agentes
4 investigaciones
4 respuestas
```

Eso sería desastroso.

El sistema necesita:

```text
fingerprint
       ↓
existing incident?
       │
   ┌───┴───┐
  yes      no
   │        │
update    create
```

OpenAI contempla explícitamente esta gestión de fingerprints y deduplicación en su ejemplo. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

# 17. El agente no debería comenzar diciendo “la causa es X”

Debe construir hipótesis.

Por ejemplo:

```text
Hipótesis A
Redis connection pool exhaustion
confidence: 0.76

Hipótesis B
Memory pressure
confidence: 0.18

Hipótesis C
Network degradation
confidence: 0.06
```

Luego necesita comprobar:

```text
¿Hay evidencia en métricas?
¿Hay logs?
¿Hubo deploy?
¿Hay PR relacionado?
¿Existe incidente histórico similar?
```

Entonces:

```text
hypothesis
     ↓
evidence gathering
     ↓
verification
     ↓
accepted / rejected
```

Esto es mucho mejor que pedirle al LLM:

> “Busca la causa raíz.”

Un simple RAG:

```text

 ↓

 ↓

 ↓
respuesta
```

Un Agente SRE:

```text
alert

decide qué herramienta necesita
 ↓
Prometheus
 ↓
interpreta resultado
 ↓
decide siguiente herramienta
 ↓
Loki
 ↓
interpreta resultado
 ↓
GitHub
 ↓
AWS
 ↓
historial
 ↓
genera hipótesis
 ↓
vuelve a consultar
 ↓

```

Eso es comportamiento agentic.

Microsoft describe precisamente la diferencia entre agente único con herramientas y orquestaciones más complejas, y recomienda comenzar con el nivel de complejidad más bajo que resuelva confiablemente el problema. # 19. Runbooks

Un componente importantísimo sería:

```text
runbooks/
├── checkout-api.md
├── payment-api.md
├── postgres.md
├── redis.md
├── kubernetes.md
└── nginx.md
```

Ejemplo:

```markdown
# Redis connection exhaustion

## Symptoms

- Connection wait time increases
- Pool usage > 90%
- Request errors increase

## Investigation

1. Check active connections
2. Check application pool configuration
3. Compare deployment version
4. Inspect Redis logs

## Remediation

1. Reduce traffic if approved
2. Restart affected deployment if approved
3. Rollback if deployment is implicated

## Verification

- error rate < threshold
- latency recovered
- queue depth normalized
```

El agente usa ese conocimiento como **operational context**.

En el ejemplo oficial de OpenAI, los runbooks se montan en `/workspace/runbooks` en modo de solo lectura, y el agente consulta el runbook correspondiente al servicio. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

# 25. Seguridad

Esta parte es crítica.

El agente tendrá acceso potencial a:


## Principio de mínimo privilegio

El agente debe tener:

```text

AWS → READ
Kubernetes → READ
```

y las acciones mutantes:


- redes seguras

- mínimo privilegio

# 28. Verificación después de la remediación

```text

   ↓

   ↓

 ┌─┴─┐

 │    │

```

# 51. Fuentes principales verificadas

La evidencia más directa es el **SRE Agent oficial de OpenAI, publicado el 10 de septiembre de 2026**, que demuestra el patrón completo de alert → investigación → telemetría/GitHub/AWS → Slack → aprobación humana. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))

Para el ecosistema de agentes, la documentación actual de LangChain/LangGraph confirma que LangChain 1.x utiliza `create_agent`, middleware, herramientas, estado y que los agentes se construyen sobre LangGraph; LangGraph incorpora persistencia, ejecución durable y human-in-the-loop. ([LangChain docs — Agents](https://docs.langchain.com/oss/python/langchain/agents))

Para la arquitectura SRE, Google documenta el uso de SLO/SLI para crear alertas accionables y considera los postmortems una pieza esencial de la práctica SRE. ([Google SRE — Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/))

Para observabilidad, OpenTelemetry documenta trazas, métricas y logs, además de patrones de deployment del Collector agent/gateway. ([OpenTelemetry — Observability primer](https://opentelemetry.io/docs/concepts/observability-primer/))

Para infraestructura, Prometheus ofrece las APIs de consulta y Alertmanager gestiona agrupación, deduplicación, silenciamiento e inhibición; Loki expone APIs HTTP para consultar y hacer tail de logs; Kubernetes mantiene un cliente Python oficial. ([Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/))

## Conclusión técnica

**Sí: el proyecto puede hacerse con el ecosistema Python de extremo a extremo.**

La arquitectura que tiene más sentido para una versión profesional es:

**Python + FastAPI + LangChain/LangGraph + PostgreSQL + Redis + Prometheus + Loki + OpenTelemetry + Kubernetes + GitHub + Slack**, y **Streamlit como panel frontend opcional**.

Y hay una razón especialmente fuerte para hacerlo: en septiembre de 2026 ya no es una idea teórica. **OpenAI tiene un ejemplo oficial de SRE agent que implementa prácticamente este patrón exacto**, y las piezas de LangGraph, observabilidad, Kubernetes, Prometheus, Loki y FastAPI necesarias para construir una variante propia están disponibles en Python. ([OpenAI Cookbook — SRE agent / sev_bot](https://developers.openai.com/cookbook/examples/agents_api/apps/sev_bot/readme))
